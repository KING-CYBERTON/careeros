# Phase 3 — Admin & Billing: Phase Plan

**Status:** Approved by Opus (2026-11-02) for the tasks that do not depend on an open decision. D1, D2 prices and D10 wait on Stephen. **Exit tag:** `0.3.0`. **Estimate:** 2 to 3 weeks.
**Starts when:** now. Phase 2 has exited; the `v0.2.0` tag waits only on Stephen pushing it.

## Goal

An organization can pay for CareerOS, and the platform can run it as a business. Org owners choose a plan, pay by card or M-Pesa, and add seats. Every platform AI call is metered against the plan's quota. Platform staff run all orgs from a Super Admin console, and org admins run their own org from an Org Admin console.

## Exit criteria (PRODUCT.md §13)

1. In staging, in payment test mode, a test org subscribes to a plan, adds seats, and hits its AI quota. It gets the 80% warning, then the hard stop at 100%.
2. Seat limits, suspension and plan features are enforced on the server, not only hidden in the UI. Q01 covers this.
3. Payment webhooks are signature-checked, idempotent and isolated. A webhook can only ever change the org named in the provider's verified metadata.
4. Super Admin actions on another org go only through audited, definer-function paths. `careeros_app` still has no BYPASSRLS. Impersonation is time-limited, shown on screen and written to the audit log.
5. Opus review: no open Critical or High findings.

| D1  | **Open (Stephen): payment providers.** Stripe does not onboard Kenya-registered businesses. Options: **A.** Paystack only. It takes cards and M-Pesa in Kenya through one integration (to be confirmed against Paystack's current Kenya docs at spec time). **B.** Stripe through a US entity (Stripe Atlas), plus Safaricom Daraja for M-Pesa, as PRODUCT.md §8.8 assumes. **C.** Paystack for cards, plus Daraja directly for M-Pesa. **Recommendation: A**, because one integration covers both payment methods and needs no foreign entity. The billing core (T04) uses a provider interface either way, so Stripe or Daraja can be added later without touching plans, seats or quotas. Manual invoicing (super admin marks an invoice paid) is built regardless, for institutions.                                                                                    |
| D2  | **Plans are data.** A `plan` table (§6.2) holds name, monthly and annual prices in USD and KES, seat limit, AI credits per seat per month, and `features` (jsonb). It is seeded with Starter, Pro and Enterprise at **placeholder prices** until Stephen sets them (§15.4). A trial is 14 days with 5 seats (§8.8). Prices are never hard-coded in the UI; they always come from the table.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| D3  | **Org lifecycle and entitlements.** `organization.status` is `trial`, `active`, `past_due` or `suspended`. One server function, `getEntitlements(orgId)`, returns the plan's features with flag overrides applied, the seat limit, AI credits and status. Every gate reads it. Seats are checked when an invitation is created and when one is accepted. `past_due` keeps working for a 7-day grace period, then becomes `suspended`. A suspended org can sign in and export its data but cannot write; the API returns `ORG_SUSPENDED`. The personal orgs created at signup are on a free `personal` plan with no admin features and a small AI quota.                                                                                                                                                                                                                     |
| D4  | **Feature flags.** A `feature_flag` table with a nullable `organization_id` (null means global), a key and `enabled`. Resolution order: the org's flag, then the plan's `features`, then the global flag, then the code default. The `FLAG_*` environment variables stay as deployment switches and are not moved. The SPA receives the resolved flags through the existing router context `flags`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| D5  | **AI metering.** Today every AI call uses a key the user saved. Phase 3 adds a **platform Claude provider** using `ANTHROPIC_API_KEY` (Claude API only, per the project rules). It is used when the org's plan includes platform AI and the member has no key of their own. Every platform call writes an `ai_usage` row (org, user, feature, model, input and output tokens, cost in USD from a price table in code). Credits are pooled per org: seats × the plan's credits per seat. The member sees a warning at 80%, and calls stop at 100% with `AI_QUOTA_EXCEEDED`, unless a super admin allows overage for that org. Calls on a member's or org's own key are logged with zero cost and never count. Model routing follows §8.4: Sonnet for generation and Haiku for classification and extraction, configurable. The quota period follows the subscription period. |
| D6  | **Super Admin.** Platform staff are users with the Better Auth admin plugin's `admin` role, and 2FA is required. The console lives on the platform host only, never on an org host. Reads and writes across orgs go through definer functions that check the caller is a platform admin and write an `audit_log` row in the same transaction. Impersonation uses the admin plugin. It lasts at most 60 minutes, shows a banner on every page, cannot impersonate another platform admin, and is audited at start and end.                                                                                                                                                                                                                                                                                                                                                   |
| D7  | **Audit log now.** PRODUCT.md lists `audit_log` as P1, but impersonation, suspension, plan changes and manual payments need it in this phase. The table is append-only: `careeros_app` may insert, but not update or delete. Org admins see their own org's entries; platform admins see all, through a definer function.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| D8  | **Org Admin console.** This adds cohorts (§6.2 `cohort`; `member.cohort_id` already exists), bulk CSV invites (capped per upload, each row checked against the seat limit), analytics (active users, resumes, applications, interviews and offers, by cohort and date range) computed by org-scoped queries, CSV export of the same, and the AI quota view. Email templates are Phase 5 and are not in scope.                                                                                                                                                                                                                                                                                                                                                                                                                                                               |
| D9  | **Webhooks.** Each provider gets a public endpoint on the platform host that verifies the signature before doing anything else, records the provider's event id in a `billing_event` table (a duplicate is a no-op), and resolves the org only from verified provider metadata, never from the request host or body fields. State changes go through one subscription state machine in T04.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| D10 | **Open (Stephen): mobile billing.** App store rules restrict selling digital subscriptions outside in-app purchase. Recommendation: mobile shows the plan, seats and quota read-only, and offers no purchase or upgrade link. Org owners manage billing on the web. Under the parity rule this exception needs Stephen's explicit decision and a note in `.agents/docs/mobile-release-handoff.md`. The Org Admin and Super Admin consoles are web-only for the same reason; mobile keeps the member experience.                                                                                                                                                                                                                                                                                                                                                             |
| D11 | **Decided (Stephen, 2026-11-02): one go-to-market release.** Job discovery (Phase 4) and the browser clipper (Phase 5) are planned now and built alongside Phase 3, together with the Phase 6 launch basics: a production environment, backups and restore, and terms and privacy pages. Phase 3 still exits with `0.3.0` on its own criteria. The go-to-market release is the first `1.0.0-rc.N` candidate on staging.                                                                                                                                                                                                                                                                                                                                                                                                                                                     |

## Risks

- **Money and quotas are security-relevant.** Every gate is on the server. The Opus review treats a way round a seat limit or quota like a tenant leak.
- **Webhooks** are the main new public surface. They need signature-first handling, a size limit, rate limiting and replay protection.
- **Platform admin power.** No BYPASSRLS. Every cross-org path is a definer function with an audit write, reviewed one by one.
- **AI cost.** A wrong price table or a missed metering path costs real money. Q01 checks that every platform-key call path writes `ai_usage`.
- **Provider availability in Kenya (D1)** must be confirmed against the provider's live docs before T05 is specced.
