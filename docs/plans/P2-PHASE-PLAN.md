# Phase 2 — White-label: Phase Plan

**Status:** Approved (Opus, 2026-11-01), except **D2** and **D3**, which are escalated to Stephen (they involve DNS, certificates and possible spend). **Exit tag:** `0.2.0`. **Estimate:** 1 to 2 weeks.
**Starts when:** Phase 1 has exited (staging verified with the role split). Specs that need no staging, T01 to T04 and Q01, may start before that.

## Goal

Each organization appears as its own product. It has its own name, logo, colours, favicon, email sender and legal links, served on its own subdomain or custom domain with automatic TLS. Upstream branding is gone from the UI, and the MIT notice stays.

## Exit criteria (PRODUCT.md §13)

1. In staging, two orgs on different hosts each show distinct branding on these surfaces:
   - the sign-in page, the app shell, the browser title and favicon;
   - the transactional emails;
   - public resume pages.
2. A custom domain added by an org admin gets verified and serves TLS automatically. Removing it stops it serving.
3. The request's host decides the org (D4). A session from Org A's host cannot act in Org B on Org B's host. This is covered by an e2e host-isolation spec and an extension of the cross-org fuzz.
4. A grep gate in CI finds no upstream product name or logo in user-facing UI strings. It allows `NOTICE`, the licenses page and code identifiers.
5. Opus review: no open Critical or High findings.

## Key decisions

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | **Branding is data, not a build.** Add an `organization_branding` table with one row per org. It is tenant-scoped with RLS and holds the fields in §6.2. Logos and favicons go in existing storage under an org prefix. The server loads branding by host and injects it into the HTML shell in `apps/server/src/static/web.ts`, the same place that injects SEO metadata today: CSS variables, title, favicon, and a JSON `window.__BRAND__` the SPA reads at boot. No per-org build. The public lookup is a hostname-only definer function (D10 pattern), and it returns only public branding fields.                             |
| D2  | **Escalated (Stephen): host naming.** PRODUCT.md assumes `<slug>.careeros.app`, and the product name and primary domain are still open (§15.1). For **staging** I recommend `<slug>.careeros-staging.ayopa.co.ke` through a wildcard Cloudflare Tunnel route. That is a second-level wildcard, so Cloudflare's free Universal SSL does not cover it. It needs Advanced Certificate Manager (about USD 10 per month). The free alternative is the first-level form `<slug>-careeros.ayopa.co.ke`, which needs no spend. Recommendation: the free first-level form for staging now, and decide the production base domain with §15.1. |
| D3  | **Escalated (Stephen): custom-domain TLS.** Option A is **Cloudflare for SaaS** custom hostnames. The first 100 hostnames are free, it needs a Cloudflare zone for the fallback origin and an API token with SSL-and-certificates edit rights, and it works through the existing tunnel. Option B is **Caddy on-demand TLS** with an `ask` endpoint. That needs inbound 80 and 443, which the home-lab VPS does not have (Q3). Recommendation: **A**. Stephen needs to enable Cloudflare for SaaS on the zone and create a scoped API token, stored as a secret, never in chat.                                                     |
| D4  | **Host decides the org.** Resolution order: (1) the host's org, from a verified custom domain or a platform subdomain; (2) on the platform's own root host only, the session's active org, as in Phase 1. On an org host the session must belong to that org. If it does not, the user sees a "join or switch" page, never the other org's data. `protectedProcedure` and `withOrgContext` stay unchanged; only `resolveOrgForAuthentication` gains the host input. API keys and MCP keep their key's org, and a key used on an org host must match that host's org.                                                                |
| D5  | **Sessions are per host.** No cross-subdomain cookies (`crossSubDomainCookies` off), so a cookie for one org's host is never sent to another's. Social and OIDC sign-in on org hosts go through the platform auth host, which hands the session back with a one-time, host-bound token (spec P2-T05). `trustedOrigins` becomes dynamic: the platform hosts plus verified org hosts.                                                                                                                                                                                                                                                 |
| D6  | **Signup on org hosts replaces D6 from Phase 1.** A signup on an org host joins that org as `member`, if the org allows open signup (a branding or settings flag, default off, so invite only). A signup on the platform root keeps the personal-org rule. Org settings live in `organization_settings`, which is tenant-scoped.                                                                                                                                                                                                                                                                                                    |
| D7  | **Two kinds of custom domain.** The upstream per-user resume domains (`custom_domain`, Traefik provider) keep working unchanged. Org domains use a new `organization_domain` table (§6.2) with statuses `pending`, `verified`, `active` and `failed`, `cf_custom_hostname_id`, and a TXT verification token. Both share the existing hostname-validation helpers. A hostname can be in only one of the two tables; a definer-function check enforces this across orgs.                                                                                                                                                              |
| D8  | **Emails.** Templates take the branding (name, logo URL, colours, sender name). The sender address stays the platform's verified address, with a per-org display name and reply-to. Per-org verified sending domains are Phase 3 or later.                                                                                                                                                                                                                                                                                                                                                                                          |
| D9  | **Upstream branding removal.** UI strings, metadata, the PWA manifest, email footers and PDF metadata take the org's app name, with a neutral platform default ("CareerOS" until §15.1 decides). `NOTICE` and a new "Open-source licenses" page keep the MIT attribution. A CI grep gate (P2-C02) blocks regressions. The 49 English catalogue strings and 34 source files found are the starting list.                                                                                                                                                                                                                             |
| D10 | **Mobile parity.** The mobile app reads the same branding through a public endpoint by org slug. In Phase 2 it shows the logo, colours and name after sign-in, and the store listing stays platform-branded (PRODUCT.md §7 v1). Record this exception in the mobile release hand-off.                                                                                                                                                                                                                                                                                                                                               |
| D11 | **Custom CSS** in `organization_branding.custom_css` is deferred to Phase 3, behind a sanitizer and a plan feature flag. Phase 2 only offers colours and a font from a fixed list.                                                                                                                                                                                                                                                                                                                                                                                                                                                  |

## Risks

- **Auth handoff (T05)** is the riskiest piece. Spec it with a one-time token that expires within 60 seconds and is bound to both host and user. The Opus review covers open-redirect and token-replay cases.
- **Cache poisoning.** Branding is chosen by `Host`, so HTML responses must `Vary: Host`. The Cloudflare cache tags in `web.ts` must include the host.
- **Hostname collisions** between user resume domains and org domains (D7).
